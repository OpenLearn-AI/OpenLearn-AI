#### Root cause (established with runtime evidence, not assumed)
The failure signature: `TimeoutError: page.waitForSelector … waiting for locator('#username')` at `performKeycloakLogin` — reported intermittent, Profile-in-full-suite. The mechanism, proven end-to-end in this environment:

1. `frontend/lib/keycloak.ts` initializes Keycloak with a **non-silent `check-sso`** (`onLoad: "check-sso"`, no `silentCheckSsoRedirectUri`). For an unauthenticated context this performs a **full-document OIDC redirect round trip** to Keycloak (`prompt=none`) and back; the `getKeycloak()` init promise **cannot settle on the first document** (the adapter navigates away before resolving). `AuthProvider` starts this on every route mount (`app/layout.tsx`), including `/login`.
2. `frontend/components/auth/LoginForm.tsx` gated its button only on the local `isLoading` click state (`disabled={isLoading}`) — **the button is enabled while the check-sso round trip is still in flight**.
3. A click processed in that window runs `handleLogin`, which awaits the shared `getKeycloak()` promise — and is then **destroyed with the first document** when the check-sso redirect commits; the continuation never resumes, so `keycloak.login()` is never invoked. Playwright considers the click delivered and does not retry.
4. The browser lands on the second document (`/login#error=login_required&state=…&iss=…`), where init settles and the button re-enables — but nobody clicks again. The helper waits for `#username` on a page that will never navigate → the exact reported timeout.

Evidence chain (failing-run trace, mechanism-demonstration run): `GET /login → 200` → click dispatched → `GET /realms/openlearn/protocol/openid-connect/auth?client_id=openlearn-frontend&…&prompt=none&scope=openid&redirect_uri=…%2Flogin → 302` (`Location: /login#error=login_required&state=…&iss=…`) → `GET /login → 200` → **no Keycloak login-form navigation ever occurs** → final DOM is the login page with the button enabled → `#username` wait timeout. This matches the previously reported diagnostic navigation sequence and the historical failure signature exactly. The race exists in **all three specs** (they duplicate the same helper); Profile's `beforeAll` page construction made it the observed victim, and full-suite association is timing correlation, not causation — the failure is a load/timing lottery (natural reproduction was not achieved in six full-suite baseline attempts in this environment; see the matrix below), which is why the mechanism was demonstrated by temporarily widening the window (sandbox-only instrumentation, removed afterwards).

#### Changes (exactly four application files + this ledger)
1. `frontend/components/auth/LoginForm.tsx` — the submit button is additionally gated on Keycloak initialization having settled: a mount-scoped effect awaits the shared `getKeycloak()` promise (the same single init promise `AuthProvider` already started — no second initialization, no new network call) and enables the button only when it resolves; an init failure resolves the promise as `null`, re-enabling the button so a click surfaces the existing "Unable to connect…" error message instead of dead-ending. `keycloak.login()`, the redirect policy, and the entire OIDC flow are untouched. This is a product-side correctness fix, not test scaffolding: a real user clicking within the init window previously hit the same silent dead click.
2. `frontend/e2e/login.spec.ts`, `frontend/e2e/courses-crud.spec.ts`, `frontend/e2e/profile-roundtrip.spec.ts` — each click site now waits for the button's **enabled** state (`expect(signInButton).toBeEnabled({ timeout: 30_000 })`) before clicking — waiting for the actual authentication-readiness state rather than a fixed delay; the budget spans a full check-sso round trip and matches the existing `waitForURL` budget. No assertion was removed or weakened; the `#username`/`#password`/`#kc-login` real-form flow and the `waitForURL(/\/dashboard$/)` assertion are unchanged. (The specs intentionally keep their duplicated helpers — no shared fixture was introduced, so no hidden state coupling between specs.)
